# WatchGuard Cloud integration: proxy API and dashboard page

This change adds a read-only WatchGuard Cloud integration across the full stack. The Django backend gains a new proxy view (`watchguard_devices`) that authenticates to WatchGuard's OAuth2 endpoint, fetches up to 200 managed devices, and reshapes them into the dashboard's standard device schema. The React frontend gets a dedicated `/watchguard` page with summary cards, a filter bar, and a sortable table, wired into the existing sidebar and router. No existing pages or views were modified. The integration is additive: when `WG_API_BASE` is not configured, the backend returns a graceful empty response rather than an error.

Watch for: **confirmed** — module-level token cache has no mutex; concurrent Django workers will race to refresh an expiring token. **confirmed** — every auto-refresh poll (including background 60 s polls) calls `setLoading(true)`, so when the page is in an error state, users see the loading skeleton flash on every poll before the error re-appears.

**Verdict**: APPROVED

---

## High-level view

The backend proxy is self-contained in `watchguard_api.py`. It follows the same `@api_view` / `TokenAuthentication` / `IsAuthenticated` decorator chain used throughout the existing codebase, protecting the endpoint with dashboard auth before it ever contacts WatchGuard.

The module-level `_TOKEN_CACHE` is a tuple replaced in a read-check-fetch-write sequence with no lock. Under CPython's GIL this means at most a handful of redundant OAuth requests around the expiry window — not a correctness failure — but under any multi-threaded WSGI configuration the guard can be passed by two threads simultaneously.

`fetchDevices` calls `setLoading(true)` at the start of every invocation, including the 60-second background interval. While the page is in an error state, each poll briefly flashes the loading skeleton before re-rendering the error panel. The page does recover on the next successful poll since `setError(null)` runs at the top of every call.

The device list is capped at 200 results (`?pageSize=200`) with no pagination loop. The `total` field returned to the frontend reflects the fetched count, not the account's actual device count, so the summary cards will silently undercount on large accounts.

<summary>Issues (3)</summary>

1. **Token cache race on worker concurrency** — `_TOKEN_CACHE` is a module-level global mutated without a lock. Under a multi-threaded or multi-process WSGI server (gunicorn with multiple workers), two workers can each read a near-expired token, decide to refresh, and issue simultaneous OAuth requests. Neither will raise an error, but it creates redundant token fetches. Add a `threading.Lock` around the check-and-refresh block.

2. **Loading skeleton flash on background polls** — `fetchDevices` calls `setLoading(true)` at the start of every invocation, including the 60-second background interval. When the page is in an error state, each poll briefly shows the loading skeleton before re-rendering the error message. Suppress `setLoading(true)` for background polls (not for the initial mount or the explicit Refresh button) to avoid this.

3. **Silent truncation at 200 devices** — `?pageSize=200` with no pagination loop means accounts with more than 200 endpoints get a silently incomplete list. The `total` card on the page will show the fetched count, not the actual device count. Either add a pagination loop in `watchguard_devices` or document the cap so users know the number is a floor, not a fleet total.

<summary>Details</summary>

### Token cache race on concurrent workers

`_GET_TOKEN` reads `_TOKEN_CACHE`, checks the expiry, and writes back a new tuple if the token needs refreshing. Under CPython's GIL, the tuple assignment itself is atomic, but the read-check-fetch-write sequence is not: two threads can both pass the `expires_at - now > 300` guard before either has written the new token. In practice this means at most a handful of redundant OAuth requests around the refresh window, not a correctness failure. Under a multi-process WSGI setup (separate gunicorn workers), the cache is per-process anyway, so the race is bounded. A `threading.Lock` would eliminate it cleanly:

```python
import threading
_TOKEN_LOCK = threading.Lock()

def _get_token() -> str:
    global _TOKEN_CACHE
    with _TOKEN_LOCK:
        now = time.time()
        if _TOKEN_CACHE is not None:
            token, expires_at = _TOKEN_CACHE
            if expires_at - now > 300:
                return token
        # ... fetch and store
```

### Error / recovery UI on background polls

`fetchDevices` calls `setLoading(true)` unconditionally at the top, including from the 60-second `setInterval`. While the page is in an error state, every background poll triggers the loading skeleton, briefly hiding the error message before re-rendering it. The fix is to track whether a call is a background poll (vs. initial mount or explicit refresh) and skip the loading state for background calls.

### Pagination cap at 200

The device list URL uses `?pageSize=200` with no pagination loop. For accounts with more than 200 endpoints, the response truncates silently. The `total` field sent back to the frontend reflects the fetched slice, not the account total, so the summary cards will undercount on large deployments.

</details>
